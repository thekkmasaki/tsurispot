# ホームページ改善：検索×地図 方針と実測（2026-07-30）

## 背景・相談内容
ユーザーより「ホームのメインが検索と週報になっているが、検索＋地図機能にした方がよいか迷う。ただし地図はロードが重くAWSコストが怖い」と相談。

## 現状把握（コード確認）
- `src/app/page.tsx` のヒーローは**すでに「検索バー＋『近くの釣り場を探す』（/mapへの最大CTA）」が主役**。週報はページ中腹のいちセクション（line 540〜）。
- 地図 `src/components/map/spot-map.tsx` のタイルは **OpenStreetMapの無料タイル**（`tile.openstreetmap.org`）。**AWSを経由しない**＝地図表示でApp Runner課金は増えない。
- 地図は `map-wrapper.tsx` で `ssr:false` のクライアント遅延読込。

## 実測（本番 tsurispot.com / モバイルUA / Cloudflare HIT）
| ページ | HTML圧縮転送 | HTML展開後 | 初期共有JS | TTFB |
|---|---|---|---|---|
| ホーム `/` | 45 KB | 443 KB | ~700 KB | 121ms |
| 地図 `/map` | **545 KB** | **3.82 MB** | ~700 KB | 113ms |

- 計測手段: PSI API はキー無し枠が枯渇（429）。代わりに curl でHTML実サイズ＋`<script>`/preload由来の初期JSを実測。
- `/map` のHTMLが激重な原因: `map/page.tsx` が `toMapSpots(fishingSpots)` で**全7,600スポットをHTMLに丸ごと埋め込み**。

## 結論と推奨
1. **ホームに"生きた地図"は埋めない**。埋めるとホームHTMLが 45KB→545KB超（約12倍）＋Leaflet JS で、今の軽いホームが台無し。CWV/SEO/直帰率に悪影響。**真のリスクはAWSコストではなくページ重量**。
2. ホームには**軽い"地図の入口"**（静的プレビュー画像＋`/map`リンク）を追加。増分ほぼ0KB。視覚的発見体験だけ取り込む。
3. **`/map`自体の最適化**（別タスク・地図の置き場所と独立）: 全件HTML埋め込みをやめ、ビューポート範囲だけ読み込む方式へ。545KB→数十KBが狙える。
4. 週報は**ホーム中腹に縮小して残す**（SEO資産として維持、ファーストビューは検索＋地図入口に集中）。
5. （将来）月50万PV時のOSMタイル規約リスク → Cloudflare経由キャッシュ or MapTiler/Protomaps無料枠を検討。

## C案（現在地ミニ地図バンド）実装メモ ※配置・未許可挙動 確定（2026-07-30）
- 配置: **ホーム ヒーロー直下**（確定）。
- 挙動: 位置情報許可時 → 近い順3〜5件＋距離＋スポット種別バッジ＋「全部を地図で見る→ /map」。
- 未許可/取得前/失敗時: **「現在地を許可して探す」ボタンを表示**（確定。人気エリア等の代替リストは出さず、ボタン主体のシンプル構成）。
- ミニ地図: **本物のLeaflet地図を、ボタン押下後にだけ遅延マウント**（確定）。CSS/SVGはチープなので不採用。初期ホームはLeaflet/タイル0のまま、押した人にだけ実地図＋近くのピン。無料・APIキー不要。OSMタイルは押した人の分だけ＝規約リスク小。
- 近い順ロジックは既存流用（`near-me-client.tsx` / `spot-map.tsx` の Haversine）。
- CWVガード: ホーム45KBを大きく増やさない。**全スポット座標は初期HTMLに埋めず、静的座標API（`/api/spots/coords`, force-static＝CDN配信）をボタン押下時に1回fetch** → クライアントで近い順計算。AWS毎回課金なし。
- 実装ファイル: `src/app/api/spots/coords/route.ts`（静的座標）/ `src/components/home/nearby-band.tsx`（バンド, idle状態はSSRしてCLS/初期表示を確保）/ `src/components/home/nearby-mini-map.tsx`（Leaflet, dynamic ssr:false）/ `src/app/page.tsx`（ヒーロー直下に挿入）。
